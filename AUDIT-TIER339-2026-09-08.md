### 🟡 LOW (3 items, deferred — not blockers)

#### L1. `audit-log.extension.ts:79` — `stableStringify` doesn't
handle BigInt / Prisma.Decimal (commented as "round 2 cleanup tier")

**Impact:** If a future audited model adds a BigInt or Decimal
field, the hash would serialise as `{}` (BigInt has no own
enumerable props; Decimal's toJSON returns a string, which
works, but is inconsistent).

**Mitigation today:** None of the current AUDITED_MODELS
(Customer, Invoice, InvoiceItem, Product, Expense, Voucher,
RecurringInvoice, Reminder, BankStatement, BankTransaction,
Attachment, Supplier, CashBookEntry, Account, JournalEntry,
VatValidationResult, FinTsTransfer, ErrorEvent) carry
BigInt/Decimal at the JSON level. Invoice carries
`Decimal` (subtotal/totalVat/total) — but `Decimal.toJSON()`
returns a string, so the current Date-only path works
incidentally. Date is the only field type that needs explicit
handling and it's covered.

**Action:** None now. When a new BigInt field is added to an
audited model, add a handler here. The comment in the source
already flags it.

#### L2. `exchange-rate.service.ts:235` — `parseCsvLine` is
naive split-on-comma (no quote handling)

**Impact:** ECB's current CSV format has no embedded commas
or quotes, but if ECB ever changes format (e.g. a currency
description column with quoted text), the parser would
silently misalign columns.

**Mitigation:** The parser checks `header.indexOf('CURRENCY')`
etc. and throws if any column is missing — the failure mode
is loud, not silent. Plus the daily @Cron logs+swallows errors
and keeps the previous cache.

**Action:** None now. If a future ECB format change breaks
the parser, the fix is one-liner (use a CSV lib). Acceptable
risk for the 7 currencies we support.

#### L3. 15 e2e scripts lack `set -euo pipefail` (deferred)

**Files:** `154-tier224-girocode-qr.sh` through
`169-tier247-dryrun-validate.sh` (all tier 154+).

**Impact:** A failed intermediate command in one of these
scripts doesn't abort the test, so a "PASSED" banner can
hide a real failure. CI run #312 didn't surface any — all
15 passed. The pattern is "each test step is wrapped in a
function that echoes its own PASS/FAIL".

**Action:** Out of scope for this session. Pre-existing
pattern from Tier 154-247 (2026-08-23). Future tier:
add `set -euo pipefail` in a single PR touching all 15
files. Not deploy-blocking.

### Bash

- 0 `mavis-trash` calls outside `|| true` guards

### Prisma
- Migration history is monotonically sorted
  (`20260718230308` → `20260905000001`)
- `20260905000001_invoice_eur_aggregation/migration.sql` uses
  `ADD COLUMN IF NOT EXISTS` (idempotent) and `WHERE
  "exchangeRate" IS NULL` (safe re-run)
- Schema column types match migration:
  `Decimal(12,6)` for exchangeRate, `Decimal(12,4)` for the
  three EUR amount columns

### Audit log hash chain
- `computeAuditHash` uses stableStringify (sorted keys,
  Date → ISO, but BigInt/Decimal deferred per L1)
- `writeAudit` is wrapped in try/catch — audit failure
  never poisons the user-facing request
- `verify` endpoint at `audit.service.ts:768` includes
  `companyId: null` rows (system events) explicitly via
  the `includeNullCompanyId` flag — `list` excludes them
  by default (correct)
- Race condition: two concurrent writes can both see the
  same `previousHash`; documented in the code comment at
  `audit-log.extension.ts:413-427` as a "verify may report
  a broken chain immediately after a concurrent burst"
  caveat. Acceptable for a GoBD audit log.

### Authentication
- `api.ts:120-131`: 401 auto-logout excludes `/portal`
  (token-based auth) and `/login` — correct.
- `api.ts:90-137`: throwOnError=true is the default; the
  401 special-case is in the throw path, so the original
  ApiError still surfaces to caller's catch. Correct.

### SQL injection
- All `$queryRaw` / `$executeRaw` template literals in the
  audited files use tagged placeholders (Prisma.sql) for
  user-controlled values.
- The two `$executeRawUnsafe` call sites
  (`invoice.service.ts:238-242`, `recurring.service.ts:854-859`)
  are guarded by year ∈ [1000,9999] AND type ∈ `/^[A-Z]{2,5}$/`
  validation. seqName becomes
  `invoice_seq_<2-5 uppercase letters>_<4-digit year>` —
  closed alphabet, no injection surface.

### XSS
- `search.service.ts:571-587`: escape-then-wrap. Source
  text is HTML-escaped first, then `<mark>` is wrapped
  around matches. The matched substring `m` is from a
  regex match against the already-escaped text, so it
  can never reintroduce unescaped HTML. The `term` itself
  is regex-escaped (`[.*+?^${}()|[\]\\]` → `$$$&`).
- 5 entities where snippets are returned to frontend
  (Customer, Product, Invoice, BankAccount, BankTransaction)
  all use the same `markTermsInText` helper. Consistent.

### Information disclosure
- `audit-log.extension.ts:163-167` SENSITIVE_FIELDS strips
  `passwordHash`, `passwordResetToken`, `twoFactorSecret`
  from oldData/newData before write. ✅
- `MAX_JSON_BYTES = 8KB` truncation prevents audit log
  blow-up from large Profile blobs.

### Race conditions
- `audit-log.extension.ts:428-433`: `previousHash` lookup
  outside the create call. Race window documented but
  impact is "verify may report broken chain after burst
  burst" — not data corruption.
- `nextInvoiceNumber`: sequence `nextval()` is atomic
  (PG-level), so concurrent invoice creates are safe.
  The `@@unique([companyId, invoiceNumber])` constraint
  is the final guard.

### Error handling
- All cron tasks wrap with `CronHealthService` (admin
  dashboard surfaces "last ran N hours ago" + last error).
- `audit-log.extension.ts:480-485`: audit write failure
  is logged but doesn't fail the user request. Correct
  pattern — audit is "best effort", not blocking.
